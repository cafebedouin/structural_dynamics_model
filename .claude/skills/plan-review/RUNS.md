Note (2026-08-23, GRAMMAR LANDED — OQ-337 mitigation): ids are no longer claimed at planning time. A planning session COMPOSES its row with the literal placeholder `<allocated-at-append>` and carries it in the checkpoint deliverable and the executor prompt; the first write-capable session to touch the run ALLOCATES the id by deriving it from this file at that moment, and appends. A planner never claims an id — every collision in this ledger's history came from one that did. The full grammar (allocation command, the three-link landing chain, the provenance-field position, the lander's two-modifications rule, the retroactive path) lives in `.claude/skills/plan-review/SKILL.md`. A machine check rides the gate as row `ledger grammar` (`python/runs_ledger_check.py --check`): it enforces row arity, id grammar, date agreement, id UNIQUENESS, the mandatory `post-impl gaps:` prefix, and the absence of unfilled placeholders. **It CANNOT see a missing append** — a run that never landed a row leaves this file perfectly grammatical, and that half is the procedure's job, not the gate's. Registered as instance four; the fourth was caught the same way as the third, by an executor re-deriving a pin instead of trusting it.

Note (2026-08-23, WHAT THIS FILE COUNTS — operator-ruled): a row records a run that reached a landing-capable session. **A plan SHELVED at checkpoint never lands a row, so the rounds it spent are not counted here.** That is a real undercount, and it falls on exactly the case this meter was built for: a loop that spends six rounds and produces nothing shelved is invisible spend, and this file does not see it. The operator saw that spend in the checkpoint deliverable at the time it happened; the longitudinal record does not. So read a monthly total here as **cost of runs that landed**, never as cost of the loop — if the meter looks cheap, this sentence is why.
