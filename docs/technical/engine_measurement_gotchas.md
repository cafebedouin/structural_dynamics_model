# Engine Measurement Gotchas — binding the corpus, and measuring old commits

Generated 2026-05-31 during a VERIFY-OR-CORRECT audit (re-cutting the row-23 / NL-gate
session cold). Scope: three ways a corpus-wide *measurement* silently returns the wrong
number while looking right — distinct from wiring bugs, these are query/setup mistakes the
auditor makes. Each was hit and caught this session; each was caught by a **positive
control** (an empty/odd result is a fact about the probe, not the corpus, until the probe
is shown to fire). See `build_discipline.md` → *Every diagnostic needs a positive control*.

---

## 1. Bind the corpus key from its generator — the predicate will not enumerate the corpus for you

**The rule:** when you census a per-constraint (or per-kernel) predicate over the whole
corpus, **bind the key from an explicit generator** and let the *measured* argument stay
unbound. Do **not** call the predicate with the key unbound and trust it to enumerate the
corpus — most engine predicates only generate the key through whichever subgoal happens to
generate first, which is a **subset** (or, the other way, an unintended **cross-product**).

**Two instances, opposite failure shapes:**

- **Signatures — key-unbound UNDER-enumerates.** `constraint_signature(C, Sig)` with `C`
  unbound does not walk the corpus; it backtracks only through the first generating subgoal
  of each cascade clause (e.g. `constraint_claim(C, mountain)`), a small subset. Witnessed
  this session: `findall(Sig, constraint_signature(_, Sig), S)` returned **1** total
  solution corpus-wide, and the `natural_law` census returned **0** — both false. Binding
  `C` over the generator returned **194** classified constraints and `natural_law` = **2**
  (the true values). The under-enumeration looks exactly like a real empty/near-empty result.

  ```prolog
  % CORRECT signature census: bind C from the generator, Sig unbound, post-filter.
  covering_analysis:all_corpus_constraints(Cs),
  findall(C, ( member(C, Cs),
               once(signature_detection:constraint_signature(C, Sig)),
               Sig == natural_law ), NLs).
  ```
  (This completes `signature_detection_wiring.md` §1: *Sig*-unbound is necessary but **not
  sufficient** — *C* must also be generated by `all_corpus_constraints/1`, not by
  `constraint_signature` itself.)

- **Kernel divergence — key-unbound OVER-enumerates (cross-product explosion).**
  `cs_kernel_divergence(K, Ctx, C1, C2)` with `K` unbound makes
  `cs_readings_for_kernel(K, …)` collect **every** constraint as a "reading," exploding the
  pair space. Witnessed: K-unbound returned **405969** solutions; binding `K` from
  `cs_kernel_id/2` first returned **79** pairs / **7184** per-context tuples — the true
  values. The engine already encodes this rule at `json_report.pl:1361` ("K must be bound
  before calling cs_kernel_divergence to avoid cs_readings_for_kernel collecting all
  constraints as readings") — the canonical census binds `K` from `cs_kernel_id` first:

  ```prolog
  findall(K, narrative_ontology:cs_kernel_id(_, K), Ks0), sort(Ks0, Kernels),
  findall(K-Ctx-C1-C2, ( member(K, Kernels),
                         cs_kernel_registry:cs_kernel_divergence(K, Ctx, C1, C2) ), Rows).
  ```

**Diagnostic:** any corpus census that returns a suspiciously round small number (0, 1) or
a suspiciously huge one is a binding smell. Bind the key from its generator and re-run; if
the number moves by orders of magnitude, the key was unbound.

## 2. Kernel divergence: the per-context SET, not the pair COUNT, is the load-bearing measure

`cs_kernel_divergence/4` has two distinct aggregations, both requiring `K` bound (§1):

- **pair count** = `sort` of `K-C1-C2` (drop `Ctx`) → distinct diverging reading-pairs.
  This is what `json_report.pl:1373` persists as `cs_kernel_divergence_count` (= **79**).
- **per-context set** = `sort` of `K-Ctx-C1-C2` → distinct (pair, context) tuples. **Not
  persisted anywhere** — only the count is.

A change can leave the pair count identical while the per-context set moves. The row-23 fix
(replacing the fabricated `Supp=0.5` in `classify_at_time`) held the pair count at **79**
but moved the per-context set **6542 → 7184 (+642)**: the fabricated constant had been
*homogenizing* real per-context divergence into false agreement. **When you change a value
that feeds `classify_at_time`, check the per-context SET, not just the persisted count** — a
count-identity check would report "no change" while the framework's actual product (the
inter-lens diff) moved. (`cs_kernel_divergence` routes through `classify_at_time` at
`cs_kernel_registry.pl:62`, so any temporal-classification change reaches it.)

## 3. Measuring an OLD commit: `git worktree` + copy in the gitignored `domain_registry.pl`

To witness a pre-fix engine value (rather than take it from a doc), run the old code in a
throwaway worktree at the parent commit:

```bash
git worktree add -d /tmp/wt-prefix <fix_commit>~1
cp prolog/domain_registry.pl /tmp/wt-prefix/prolog/domain_registry.pl   # see below
cd /tmp/wt-prefix/prolog && swipl -q -g "[stack], corpus_loader:load_all_testsets, …"
git worktree remove --force /tmp/wt-prefix
```

**The silent gotcha:** `prolog/domain_registry.pl` is **gitignored** (`.gitignore:8`) and
**generated** — it exists in the main working dir but is **absent from a fresh worktree's
tree**. The old `domain_priors.pl` does `use_module(domain_registry)`, so the worktree load
emits `ERROR: source_sink 'domain_registry' does not exist` and `domain_priors` fails to
load. **This corrupts every `domain_priors`-dependent result** — metrics, `constraint_signature`,
`dr_type` — while leaving non-`domain_priors` queries (`classify_at_time` →
`cs_kernel_divergence`) working. So the breakage is easy to miss: half your queries return
trustworthy numbers, half return wrong ones, and only the load ERROR (often buried in
output) distinguishes them. **Copy the main working dir's `domain_registry.pl` into the
worktree** before relying on any metric/signature number, then re-run and confirm stability.

**Corpus-drift check:** before trusting a pre-fix-vs-HEAD diff as engine-only, confirm the
worktree and HEAD have the **same `testsets/` count** (`ls prolog/testsets/*.pl | wc -l`).
This session all three commits showed 226 — so the diff isolated the code change cleanly. If
they differ, the comparison is confounded by corpus growth, not just the fix.

**Worked example (this session):** parent-of-`39630182` (pre row-23) gave per-context set
**6542**; HEAD gave **7184** — both observed, neither taken from the handoff. Parent-of-
`3116ac08` (pre NL-gate) gave raw `natural_law_signature` match **5**; HEAD gave **2** — the
3 declined (`behavioral_competence_reading`, `disparity_as_depth_signal`,
`generational_economic_decline`) identified by set-diff, each confirmed to carry ≥1 authored
`constraint_beneficiary`. The first pre-NL-gate run returned a wrong-looking signature
census *because `domain_registry.pl` was missing* — caught by the load ERROR, fixed by the
`cp`, re-run to the trustworthy value.
