## 2. Project Overview

### What It Does
A Prolog-based classification engine for structural dynamics analysis. Constraints (social, economic, political structures) are classified into types — mountain, snare, rope, tangled_rope, scaffold, piton, naturalized — based on extraction metrics (ε), power-scaled extraction (χ = ε × π(P)), suppression scores, and structural signatures.

### Who It's For
Researchers and analysts studying how constraints operate across power differentials. The Streamlit app (`agent/app.py`) provides a public-facing interface for generating and analyzing constraint narratives.

### Main Components
- **Prolog engine** (76 modules, 30,015 LOC): Classification, validation, reporting
- **Python tooling** (67 files, 30,333 LOC): Linting, pipeline orchestration, statistical analysis
- **Streamlit app** (`agent/app.py`): Public UI for constraint story generation
- **910 testsets** (`prolog/testsets/`): One per constraint, each a self-contained Prolog scenario
- **Narrative transform pipeline** (`agent/narrative_transform/`): Multi-stage story generation

### Public Surfaces
- **GitHub repository**: Source code, testsets, documentation
- **Streamlit app**: Deployed with secrets management via `st.secrets`

### Corpus Provenance
Testsets are generated by both Gemini and Claude models — this is intentional for cross-model comparison, not a fallback pattern. The `agent/uke_narrative_orchestrator.py` (1,641 LOC) handles multi-model orchestration explicitly.

## 3. Architecture & Design Review

### Strengths

**S1. Single Source of Truth for classification.**
`classify_from_metrics/6` in `drl_core.pl:164-385` is the sole threshold predicate. Verified via `audit_data/verify_delegation.txt`: 12 external modules call it, and the 4 documented delegation modules (drl_core, drl_modal_logic, drl_lifecycle, data_validation) all route through it. No competing classification logic exists.

**S2. 31-check linter with 41 distinct error codes.**
`python/linter.py` (719 LOC) implements 31 numbered validation checks producing 41 error codes — covering structural completeness (MISSING_BENEFICIARY, MISSING_VICTIM), metric consistency (FLOOR_EXCEEDS_EXTRACTION), and authoring guidance (IDENTICAL_EXIT_OPTIONS). This is a genuinely thorough data validator.

**S3. Dual-threshold architecture (χ AND ε).**
Classification requires both power-scaled extraction (χ) and base extraction (ε) to exceed thresholds. Verified in `drl_core.pl:323-366` — snare, rope, and tangled_rope clauses all check both. This prevents power-atom gaming.

**S4. Signature override system.**
`structural_signatures.pl` + `signature_detection.pl` (1,095 LOC) provide a secondary classification pathway. Natural Law signatures override metrics unconditionally (`drl_core.pl:300-312`). Constructed constraint signatures are split into 3 extraction-aware sub-signatures (`signature_detection.pl`).

### Weaknesses

**W1. `scenario_manager.pl` fails to load `data_repair`.**
`scenario_manager.pl:7-8` loads only `narrative_ontology` and `test_harness`. Line 110 calls `data_repair:repair_interval(ID)`. When `validation_suite.pl` is loaded standalone, data_repair is never transitively loaded, causing `existence_error(procedure, data_repair:repair_interval/1)`. The retry with explicit `['data_repair']` succeeds with 910/0.

**Fix**: Add `:- use_module(data_repair).` to `scenario_manager.pl`.

**W2. 17 directionality constants bypass config.pl.**
`constraint_indexing.pl:313-334` hardcodes:
- 11 `power_role_heuristic/4` values (0.10 to 0.90)
- 6 `exit_modulation/2` values (-0.03 to 0.05)

These directly control χ computation but are invisible to `config_sensitivity_sweep.py`. A new companion sweep (`directionality_sensitivity_sweep.py`) confirms all 17 are **Inert at ±25%** — so the stability conclusion holds, but the architectural concern remains: these values are not tunable via `config.pl` and would require code changes to modify.

Some values (0.46, 0.72) coincidentally match config params (`snare_epsilon_floor`, `canonical_d_analytical`) but serve different logical purposes.

**W3. 40 unused config params — config sprawl.**
`audit_data/config_params_unused.txt` lists 40 params declared in `config.pl` but never referenced in executable `.pl` code. Categories:
- `contamination_strength_*` (7 params) — legacy from pre-v5 architecture
- `boltzmann_floor_*` (6 params) — referenced only in `python/` and `config_schema.pl`
- `complexity_offset_*` (6 params) — same pattern
- `constructed_*_min` (3 params) — schema-only
- `network_*` (3 params) — docs-only
- `version`, `logic_engine` — truly dead (not even in schema)

These params inflate the config without affecting classification. The sensitivity sweep sweeps 150 of 170 params — the 20 gap is mostly these unused params plus a few non-numeric ones.

**W4. Linter cannot be invoked from command line.**
`python/linter.py` has no `if __name__ == "__main__"` block. The plan's command `python3 python/linter.py prolog/testsets/` produces zero output (0 bytes). Must be imported as `from linter import lint_file`.
